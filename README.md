# Web Serial Tool · 串口助手

基于 [Web Serial API](https://developer.mozilla.org/docs/Web/API/Web_Serial_API) 的浏览器串口调试工具。打开网页即可收发数据，无需安装驱动或客户端。

## ⚠️ 使用前须知

本工具会向**真实硬件**发送数据，发出去的字节会产生物理后果：

- 内容或波特率写错可能刷坏固件、把设备变砖；
- 报文可能触发继电器、电机、气缸等机械动作；
- **周期发送会一直发下去**，包括你切走标签页、隐藏面板之后 —— 这是设计如此；
- 在部分开发板（ESP32、带自动下载电路的 Arduino 等）上，**仅仅「打开端口」这个动作**
  就会通过 DTR/RTS 触发复位。

请只在你有权操作的设备上使用；接到生产设备或有安全风险的机械上时请自行评估风险。
本工具按「现状」提供，不作任何担保 —— 详见 [LICENSE](LICENSE)。

## 运行环境

| 项         | 要求                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| 浏览器     | Chrome / Edge 89+ 或其他 Chromium 内核浏览器（Firefox、Safari 不支持 Web Serial） |
| 安全上下文 | HTTPS 或 `localhost`——这是 Web Serial 的硬性要求                                  |
| 授权       | 需点「选择端口」，由用户手势触发浏览器的设备选择器                                |

浏览器不支持时页面会显示明确的说明横幅，不会假装功能可用。

### 关于端口选择与端口名

Web Serial 出于隐私考虑**不允许页面枚举系统里的所有串口**——`getPorts()` [按规范](https://wicg.github.io/serial/#dom-serial-getports)只返回本站点已获授权的端口，授权只能通过浏览器自己的选择器完成。因此本工具采用**单端口**模型：点「选择端口」打开浏览器选择器，选中即成为当前端口；选完会立刻提示给它起个备注名。选择结果会被记住，下次打开页面自动恢复。

`getInfo()` 只提供 USB VID/PID，**拿不到 COM 口名或设备友好名称**。规范里 `SerialPortInfo` 的 IDL 就三个成员：

```webidl
dictionary SerialPortInfo {
   unsigned short usbVendorId;
   unsigned short usbProductId;
   BluetoothServiceUUID bluetoothServiceClassId;
};
```

社区对此有公开诉求（[WICG/serial#175](https://github.com/WICG/serial/issues/175)），**至今未解决**；背景是 WebKit 以指纹追踪为由反对该规范，Chrome 因此把可暴露的信息压到最小。

本工具在这个前提下做两件事：

1. **把 VID/PID 翻译成芯片 / 厂商名**（如 `#1 CH340 (1A86:7523)`）。对照表在 [`src/core/transport/usbNames.ts`](src/core/transport/usbNames.ts)，只收身份明确的条目，查不到就退回原始 ID 不做猜测。
2. **让用户给端口起备注名**（显示为 `电机控制器 · #1 CH340 (1A86:7523)`），持久化到 localStorage，刷新后仍在，并跨标签页同步。

> **备注的已知局限**：备注按「VID:PID + 出现序号」存储（如 `usb:1A86:7523#0`）。虚拟串口（com0com 之类）不是 USB 设备，`getInfo()` 返回空对象，前缀退化为 `serial`，只能靠序号区分——因此**这类端口若 `getPorts()` 返回顺序变化，备注可能对调**。有各自独立 VID:PID 的设备不受影响。根因是浏览器不暴露序列号；要可靠区分同型号/虚拟设备，只能走本地辅助程序或桌面端打包（见 Roadmap）。

## 接收分帧

`reader.read()` 返回的「块」边界是**驱动与时序的产物，不是协议的边界**——同一条设备回复可能被拆成两次读取，也可能和下一条挤在一次里，取决于读取那一刻缓冲里恰好积了多少字节。接收区顶部因此提供三种分帧方式，互斥：

| 方式         | 触发条件                     | 适用                                                             |
| ------------ | ---------------------------- | ---------------------------------------------------------------- |
| **原样显示** | 不处理，读到什么就是一行     | 排查「数据到底是怎么到达的」。零延迟、行为完全可预测             |
| **空闲超时** | 静默超过 N 毫秒（默认 10ms） | 没有帧尾标记的二进制协议。Modbus RTU 的 3.5 字符间隔就是这个思路 |
| **按换行**   | 遇到 `\n`                    | AT 指令、NMEA 这类文本协议。仅 TXT 视图可选                      |

控件是**一个下拉框**，不是几个并列的开关：三者互斥，下拉框关闭状态下就写着当前生效的模式，不需要去比对哪个控件在起作用。「空闲时长」输入框只在选中「空闲超时」时才出现——同一时刻界面上只有一个跟分帧有关的可调项。把时长填成 `0` 等同于不分帧，模式会自动同步成「原样显示」，下拉框显示的和实际生效的不会打架。

几点需要清楚：

- **帧里保留分隔符**（`\n` 及其前面的 `\r`）。这是调试工具，不该悄悄吃掉字节：设备发的到底是 CRLF 还是 LF 往往正是要查的东西，而且状态栏的 RX 字节数直接来自帧长度，丢字节会让统计对不上。
- **单帧有 8192 字节上限**。否则一个只发二进制、永远不出现 `\n` 的设备会让换行分帧无限攒下去；空闲分帧在持续满速率、从不静默的链路上同样攒不完。到顶就强制成帧。
- **换行分帧只在 TXT 视图下生效**。切到 HEX 时自动回落到空闲/原样，偏好本身保留，切回来还在；此时下拉框显示的是**回落之后**的模式，而不是存着的偏好——显示一个并不生效的选项同样是误导。
- **端口关闭或掉线时，缓冲里没成帧的尾巴会被交付出来**，不会因为等不到分隔符就永远不显示——断线前的最后半条数据往往最有诊断价值。
- **速率统计与分帧无关**：状态栏的 B/s 统计链路上真实流过的字节，分帧只改变「怎么切」，不改变「收了多少」。
- 文本显示始终正确：UTF-8 流式解码器跨块保持状态，被切开的汉字不会变乱码。

## 功能

- **端口**：单端口模型，浏览器选择器授权、选完即提示起备注名、芯片/厂商名识别、在位状态标注、选择结果持久化
- **串口参数**：波特率 32 档常用值（110 ~ 3000000，含 MIDI 31250、DMX/3D 打印 250000 等）且支持直接输入任意自定义值

- **发送**：单条发送（Ctrl+Enter）、周期循环；TXT 与 HEX 各有自己的帧尾控件，同一位置互斥显示，**默认都不追加**

- HEX → 校验和（17 种算法），选中后即时显示将要追加的字节，发送时自动附加
- **预设**：分页管理，每页固定 10 条共 5 页；每条一行（勾选 · 格式 · 数据 · 发送 · 周期 · 循环），发送按钮上显示自定义名称；单条循环 / 顺序循环（跨页生效）/ JSON 导入导出

## 本地持久化

界面上的配置项都存在浏览器本地（键统一带 `wst.` 前缀），刷新或重开页面自动恢复。
支持多个页面各连一个端口之后，「存在哪」有三种作用域：

- **全局**（localStorage）：同源全部页面共享；
- **页面**（sessionStorage）：每个页面独立，刷新后仍在，关掉即消失；
- **分层**：读时页面优先、全局兜底，写时两处都写。效果是「已开的页面各改各的，
  新开的页面继承你最后一次的选择」。

| 键                   | 作用域 | 内容                                                                 |
| -------------------- | ------ | -------------------------------------------------------------------- |
| `portSettings`       | 全局   | **按设备存**的串口参数：`{ "usb:1A86:7523#0": { baudRate, ... } }`   |
| `connectionSettings` | 全局   | 最近一次用的串口参数，给新设备 / 新页面当初值                        |
| `sendPane`           | 分层   | 发送内容、TXT/HEX 模式、结束符、校验和、周期                         |
| `viewPrefs`          | 分层   | 接收区视图（TXT/HEX）、时间戳、自动滚屏、显示 TX、仅看匹配、分帧设置 |
| `selectedPort`       | 分层   | 上次选中的设备标识                                                   |
| `presets`            | 全局   | 全部 50 条预设（名称、数据、格式、周期、顺序循环勾选）               |
| `sequenceGapMs`      | 全局   | 顺序循环的间隔                                                       |
| `portAliases`        | 全局   | 端口备注（跨页面同步）                                               |
| `lang` / `theme`     | 全局   | 语言与主题                                                           |

**串口参数是按设备记的**，不是全局一份：插 CH340 自动回到 115200、插调试器自动回到
921600，比共用一份符合直觉；顺带也让多个页面各连一个端口时谁也盖不掉谁——它们写的
本来就是不同的键。设备没有存档时沿用当前参数，而不是退回出厂默认。

三条设计约定：

- **写入攒批**。发送框、预设数据格每敲一个键都会改状态，逐次 `setItem` 是主线程上的同步 IO；这里攒 250ms 一起写，并在 `pagehide` / 页面切到后台时立即落盘，不会丢最后一批改动。
- **读取逐字段校验**。存量数据可能来自旧版本、被手改、或被别的标签页写坏。任何字段不认识就退回默认值——例如越界的波特率不会被带进来变成一个必然打不开的配置。预设复用的是导入 JSON 那套校验器，没有维护两套的必要。
- **有意不存的**：接收区的**过滤词**（日志本身是内存态、刷新后为空，恢复一个针对空日志的过滤词只会制造困惑）、预设的**当前页码**（那是浏览位置，不是配置）。

localStorage 不可用时（隐私模式、站点数据被禁用、配额满）读写都会静默失败，只影响「记不住」，不影响任何功能。

全局作用域里那些**整张表一次性写入**的键（`portSettings`、`portAliases`）监听 `storage`
事件跨页面同步：否则 A 页存下的东西会被 B 页的下一次写入整体覆盖回去。

## 架构

```text
src/
  core/        纯 TypeScript，零框架依赖、零 DOM 访问，可在 Node 下单测
    transport/   Web Serial 之上的字节流通道 + 串行化写队列 + 端口身份登记
    framing/     接收分帧（空闲超时 / 换行 / 原样分块）
    codec/       UTF-8 编解码、HEX 解析、日志显示转义
    checksum/    CRC16 / SUM8 / XOR8
    scheduler/   周期任务调度、断线重连退避
    session/     把上面几层编排成一次「串口会话」
    buffer/      日志用的环形缓冲
  store/       Zustand 状态层，订阅 core 的事件
  ui/          React 组件（每个目录 = 组件 + CSS Module）
               左栏接收区，右栏上单条发送、下多条发送
  i18n/        文案目录（zh / en）
  lib/         localStorage 安全包装、偏好持久化（攒批写入 + 字段校验）、下载工具
```

分层规则由 ESLint 强制：`src/core/**` 不得 import React / zustand / ui / store，也不得直接访问 `document` 或 `localStorage`。唯一接触浏览器串口 API 的地方是 `core/transport/webSerialTransport.ts`。

`core/` 的接口（`Transport`）在测试里由 `tests/fakeTransport.ts` 实现，因此「打开 → 收帧 → 掉线 → 退避重连 → 恢复」这条链路可以在 CI 中跑成确定性测试，不需要真实硬件。

## 测试

自动化测试共 485 个单元/集成用例，另有 9 个跑在真实 VS Code 里。覆盖率统计 core / lib / store / 扩展宿主与 webview，整体 93%，
其中 core 层 98%（阈值分两档，core 更严，见 vite.config.ts）：

- **校验和**由通用 CRC 引擎（Rocksoft 参数化模型）驱动，参数与自校验的 check 值全部取自 [CRC RevEng 目录](https://reveng.sourceforge.io/crc-catalogue/all.htm)。测试逐条用目录的 check 值（`"123456789"` 的结果）验证 —— 参数抄错了 check 值必然对不上，因此这一条同时证明了引擎实现和参数表都正确
- **编解码**覆盖 UTF-8 跨块流式解码（被切开的汉字不乱码）、HEX 宽松解析与结构化报错、HEX→文本的无损往返校验
- **分帧**覆盖三种模式各自的切分规则、一行被拆到多块、CRLF 完整保留、超长强制成帧、空闲超时（fake timers）、切换模式时缓冲不卡住，以及关闭/掉线时交付尾巴
- **调度器**覆盖不重入、周期漂移修正、`stopAll` 不影响重连
- **会话**用 `FakeTransport` 驱动完整的掉线重连链路，并覆盖「关闭与在途的打开／重连尝试相竞争」—— 这条路径会让端口被孤儿会话独占
- **传输层**用基于 WHATWG Streams 的 `FakeSerialPort` 覆盖读循环退出条件、关闭时的锁释放顺序、流出错后的恢复、打开途中被关闭的时序
- **预设**覆盖导出 → 导入往返（内置项的译名不丢）与伪造 `labelKey` 的拒绝
- **持久化**用「写存储 → resetModules → 重新 import」模拟刷新，覆盖各项配置的往返，以及存量数据越界 / 损坏 / 引用了已不存在的校验和时退回默认
- **多页面**覆盖偏好作用域（页面优先、全局兜底）、每台设备各记各的串口参数、
  端口选择记在本页面，以及跨页面占用广播的认领 / 放手 / 陈旧条目自愈
- **扩展宿主**覆盖 Node 传输层的完整生命周期、端口占用仲裁、插拔轮询、
  会话编排（含多面板互不干扰）、活动栏端口视图
- **回环**（`apps/vscode/src/webview/loopback.test.ts`）把 webview 侧的 store 与宿主侧的
  会话**直接对接**跑：store → RPC 客户端 → 协议 → 宿主 → 会话 → 分帧，中间全是真代码，
  只有最底下的串口和 VS Code 消息通道被替换掉。它还能模拟「面板被隐藏」——
  掐断两侧通道，验证周期发送仍在宿主那边继续
- **协议**用 `Record<判别式, 消息>` 声明样本表，逐条过结构化克隆：
  新增一种消息却忘了加样本时类型检查会当场报错，这张表不会腐化成只覆盖一半的摆设
- **真实串口**（`npm run test:hardware`，需一对能互通的口，见下）覆盖真实驱动分块下的
  UTF-8、空闲/按行分帧的真实时序、8KB 高速接收完整性、端口的占用与释放
- **真实 VS Code**（`npm run test:vscode`）把扩展装进一个真的编辑器里跑：能否激活、
  激活时机对不对、命令注册没有、面板建不建得出来，以及**在真机上打开一个真实串口**。
  这一档抓到过一个前面所有测试都看不见的 bug（见下）。CI 里用 xvfb 跑，
  依赖真实串口的用例必须显式开启：`SERIAL_INTEGRATION_PORTS=COM3,COM4 npm run test:vscode`。
  不靠「端口列表是否为空」来自动探测 —— GitHub 的 Linux runner 上 `SerialPort.list()`
  会列出一堆 `/dev/ttyS*`，枚举得到却连不上，自动探测只会让 CI 整片红；
  开发机上更糟，可能抢走你正在调的设备
- **构建产物**有不变量断言（`apps/vscode/scripts/verify-artifacts.mjs`）：
  原生模块保持外部、bootstrap 求值早于 store、无外部 CDN 引用；
  打包时另有一轮 VSIX 内容断言（图标 / 文案 / 原生预编译产物在不在，源码有没有混进去）
- **组件**覆盖过滤高亮、TXT/HEX 切换、有损模式切换被拒绝、语言切换、格式控件三处形态与标签中英一致

### 真机集成测试抓到过什么

`SerialSession.dispose()` 曾经只断开引用、**从不真正关闭传输层**。

浏览器里这看不出问题 —— 页面一卸载，操作系统什么都释放了。但扩展宿主是长驻进程：
关掉一个面板就永久漏掉一个串口，之后再想打开同一个口只会拿到 `Access denied`，
直到 VS Code 退出。

单元测试看不见它（`FakeTransport` 不模拟操作系统资源），回环测试也看不见（同样原因）。
**只有真机上的真实串口把它逼了出来。**这就是这一档测试存在的理由。

### 新增测试时的一条经验

**写完一个测试，先把它对应的 bug 注回去，确认它真的会红。**

这不是形式主义：回环测试第一版里那条「周期发送真的跑在宿主那一侧」看着很对，
注入原始缺陷后**照样是绿的** —— 因为回环里两侧同在一个进程，任务就算跑在 webview，
它的 send 照样能通过 RPC 送到串口。必须先模拟「面板被隐藏」把通道掐断，那个区别才显形。
不做这一步，仓库里就会多一条让人安心、实则什么都挡不住的测试。

### 真实串口回环（需要一对能互通的口）

```bash
SERIAL_LOOPBACK_PORTS=COM1,COM2 npm run test:hardware
```

一对虚拟串口（com0com / HHD Bridge）或两个 USB 转串口用交叉线对接都行。
**不做自动探测**是有意的：自动去开机器上的串口很可能打断别人正在调试的设备，
启用它必须是一个明确的动作。

它接管了原来只能人工验收的几条：真实驱动分块下的 UTF-8 中文、空闲分帧与按行分帧的
真实时序、8KB 高速接收的完整性、关闭与 dispose 之后端口真的还给了操作系统。
背压那条会先探一下这对口是否真按波特率限速 —— 很多虚拟串口对不限速，
那种口上永远撞不到背压，测了只会得到一条假绿，所以它会跳过并说明原因。

**仍然只能人工验收的部分**（浏览器需要用户手势授权；有些现象机器判断不了）：

1. Chrome/Edge 打开站点 → 选择端口 → 授权 → 打开 → 收发正常
   （扩展形态下这条已由集成测试覆盖）
2. 收发中途**拔掉 USB** → 观察指数退避重连日志 → 插回 → 自动恢复
   （虚拟串口对模拟不了物理拔出）
3. 插入第二个设备后重新枚举 → 原选中端口不发生偏移
   3b. 连续授权两个同型号适配器 → 下拉框以 #1 / #2 区分；拔掉其中一个 → 标注「已拔出」
4. 10 ms 周期发送 + 9600 波特率 → 出现背压告警而非界面卡死
   （需要真按波特率限速的口；`test:hardware` 在这类口上会自动接管这条）
5. 115200 持续高速接收 → **内存平稳、界面不卡**
   （数据完整性已自动化，"平稳"和"不卡"得人眼看）
6. 往上翻阅历史日志 → 不被自动拽回底部
7. 浏览器里开两个页面各选一个不同端口 → 收发互不干扰；两边各改各的波特率互不覆盖；
   分别刷新 → 各自回到自己那个端口
   7b. 让第二个页面去选第一个页面已打开的端口 → 端口名后标注「已被其他页面占用」，
   点打开被拦下并在日志里说明原因，且不进入重连循环
   7c. 关掉第一个页面 → 第二个页面的占用标注消失，可以正常打开
   （VS Code 形态下的对应行为已由集成测试覆盖）

## 多页面并行使用

支持在同一台电脑上开多个页面、各自连接不同的端口独立工作：

- **授权是按源共享的**——任一页面授权过的端口，其他页面也能直接使用，不必重复授权；
- **每个页面各自持有一条会话**，日志、统计、周期任务都是页面内的内存状态，互不干扰；
- **端口选择、发送内容、接收区视图按页面存**（见「本地持久化」的分层作用域）。
  刷新任一页面都会回到它自己那个端口，而不是所有页面一起跳到同一台设备；
  在 A 页面打字、切 HEX 视图，也不会影响 B 页面；
- **串口参数按设备存**，两个页面连着不同的口时，各自的波特率互不覆盖；
- **同一个端口不能被两个页面同时打开**——串口在操作系统层面是独占的。
  页面之间通过 `BroadcastChannel` 互相通气：某个端口已被本工具的另一个页面打开时，
  端口名后面会标注「已被其他页面占用」，点打开会被直接拦下并在日志里说明，
  而不是让用户对着一句 `Failed to open serial port` 猜发生了什么。
  这种拦截**不会**触发自动重连（重连只在链路意外中断时启动），
  因此不会出现两个页面互相抢端口的重试风暴；
- **端口备注跨页面同步**：备注存在 localStorage 里，监听 `storage` 事件，
  一个页面改了其他页面即时跟进，不会互相覆盖；
- **浏览器标签条上能分辨谁是谁**：页面标题跟着端口走，正连着的那个前面还有一个圆点。

占用登记是**尽力而为**的，不是锁：

- 外部程序（PuTTY、Arduino IDE、其他浏览器）占用的端口这里看不见，
  真正的兜底始终是 `open()` 本身会失败；
- 页面被强杀时来不及放手，会留下陈旧登记。插拔设备时会重新广播询问、据应答重建
  占用表，只有还活着的页面才会应答，陈旧条目随之消失。也正因为可能有陈旧登记，
  「打开」按钮**不禁用**，用户始终能重试。

> 上述并行行为在 CI 中覆盖到了状态层（作用域、设备级参数、占用广播都有单元测试）；
> **「两个页面各连一个真实端口」需要在真机上验收**，见人工验收清单第 8 条。

## VS Code 扩展

同一套 core 与界面另有一份 VS Code 扩展形态，源码在 `apps/vscode/`（npm workspace 成员，
原生依赖 `serialport` 只装在它那里，不落到 Web 应用的依赖表）。

### 为什么不能直接把网页塞进 webview

VS Code 的 webview 是沙箱 iframe，**没有 `navigator.serial`**；桌面端暴露 Web 设备 API 的
诉求（[microsoft/vscode#236450](https://github.com/microsoft/vscode/issues/236450)）至今在 Backlog。
所以串口必须由扩展宿主进程用 `serialport` 打开，webview 只做渲染。

### 一个面板 = 一条会话 = 一个端口

```
┌── 扩展宿主进程 (Node) ────────────────┐        ┌── Webview (React) ────────┐
│  NodeSerialTransport (serialport)    │        │  ui/ + store/（与网页版同一份）│
│    ↓ core 的 Transport 接口（原样复用）│        │  SessionClient             │
│  SerialSession / 分帧 / 写队列 / 重连  │◄─RPC──►│    ↑ 与 SerialSession 同形   │
│  TaskScheduler（周期发送）            │ 攒批帧  │  codec/（HEX/文本渲染）     │
│  RingBuffer（日志真相源）             │        │                            │
│  PortLeases（占用权威仲裁）           │        │                            │
└──────────────────────────────────────┘        └───────────────────────────┘
```

会话活在**宿主进程**而不是 webview，这是整个设计的支点：VS Code 的 webview 一旦被隐藏
就会被销毁。会话若放在那边，用户切去看一眼代码回来就会发现串口断了、心跳停了、日志空了。
放在宿主之后，面板只是个可以随时重建的视图，重建时用一条 `snapshot` 把状态与历史回放回去。

多面板不需要在协议里编址：每个 WebviewPanel 有自己独立的 postMessage 通道，
宿主用 `Map<WebviewPanel, SessionHost>` 关联即可。

### 入口

- **活动栏的端口视图**（主入口）：左侧 🔌 图标点开是机器上现有的端口，
  **点一个就开一个连着它的面板**。已连上的口标成绿色，点它会切到对应面板而不是再开一个；
  行尾的 `+` 强制新开一个。端口枚举是惰性的 —— 只有真的展开这个视图才会去加载原生模块、
  开始轮询，没用到串口的人不为它付启动开销。
- **状态栏**：默认常驻（`serialTool.statusBar` 可调），一个面板都没有时也在，点一下即新建；
  已有面板时点它会列出全部面板供切换。
- **编辑器标题栏的 `+`**：焦点在串口面板上时出现，就地再开一个连别的口。
- **命令面板**。

一个只能从命令面板打开的工具，用户装完就找不到了 —— 常驻入口是有意的默认值。
为此扩展的激活时机是 `onStartupFinished`：留空的话要等用户先执行一次命令才激活，
而入口在那之前根本不存在，这条链是断的。

### 与浏览器版的差异

|          | 浏览器                                        | VS Code                                       |
| -------- | --------------------------------------------- | --------------------------------------------- |
| 端口枚举 | `navigator.serial.getPorts()`，需用户手势授权 | `SerialPort.list()`，无需授权                 |
| 端口身份 | `VID:PID#出现序号`（浏览器拿不到序列号）      | `usb:VID:PID:序列号`，跨插拔稳定              |
| 端口标签 | `#1 CH340`                                    | `COM3 · CH340`，与设备管理器一致              |
| 插拔感知 | connect / disconnect 事件                     | **没有事件，只能轮询**（默认 2s，可配）       |
| 占用仲裁 | BroadcastChannel，尽力而为                    | 宿主进程里的权威占用表                        |
| 偏好存储 | localStorage / sessionStorage                 | 宿主 `globalState`（可随 Settings Sync 同步） |
| 周期发送 | 页面内                                        | 宿主进程内，面板隐藏也照跑（含顺序循环）      |

运行环境的差异全部收敛在 `src/store/platform.ts` 这一个接口后面，store 与 UI 只认它 ——
复制一份 store 出来给扩展用，两边迟早会长歪。

### 构建与调试

```bash
npm run build:vscode        # 宿主用 esbuild，webview 用 Vite → apps/vscode/dist/
npm run package:vscode      # 打成 VSIX（约 1.2 MB，含全平台原生产物）
```

在 VS Code 里按 **F5**（配置「运行扩展」，见 `.vscode/launch.json`）会开一个扩展开发宿主窗口，
在里面执行「新建串口面板」即可试用；断点直接打在 `apps/vscode/src/host/` 的源码上。

`serialport` 及其原生绑定**不打进 bundle**：`@serialport/bindings-cpp` 靠 node-gyp-build
在运行时按 `__dirname` 去自己的包目录找 `prebuilds/<平台>-<架构>/*.node`，打平就找不到了，
必须以「一个完整的包」的形态跟着 VSIX 走。

打包是在**仓库之外的一个临时目录**里做的（`apps/vscode/scripts/package.mjs`）。
直接在扩展目录里 `vsce package` 会踩两个坑：workspace 把依赖提升到了仓库根目录，
vsce 顺着提升后的路径算出 `extension/../../vite.config.ts` 这种跑出扩展目录的相对路径而报错；
若在本地再铺一份依赖，它又会把同一批文件从两个位置各收一遍，撞上「同名路径」错误。
搬到没有 workspace 祖先的地方，这两个问题就都不存在了。

当前打出的 VSIX 含 13 个原生产物，覆盖 win32 x64 / arm64 / ia32、
linux x64 / arm / arm64（musl 与 glibc 各一份）、darwin 通用二进制、android。
体积只有 1.2 MB，暂时没有拆平台包（[platform-specific extensions](https://code.visualstudio.com/api/working-with-extensions/publishing-extension#platformspecific-extensions)）的必要。

### 已知限制

- **端到端验收只走了一部分**：已在扩展开发宿主窗口里跑通「打开端口 → 收发正常 →
  切走标签页后接收不断」。周期发送在宿主执行这条刚修好（此前所有任务都漏传了 frames，
  于是退化成在 webview 里跑，面板一隐藏就停），**还需要在真机上复验一遍**。
  README「测试」一节的人工验收清单其余各条也尚未在扩展形态下走过。
- 原生模块加载失败时（个别平台/架构缺预编译产物、或被安全软件拦截），扩展会捕获并给出
  提示 + 浏览器版兜底链接，而不是白屏。serialport v13 的预编译覆盖面已经相当完整
  （含 Windows ARM64 与 musl），这条更多是兜底而非常态。

## 发布

### 网页版

推送到 `main` 即自动部署（见下节）。

### VS Code 扩展

打 tag 就发布，`.github/workflows/release.yml` 会依次做：跑完整 CI → 校验 tag 与
`apps/vscode/package.json` 的版本号一致 → 打 VSIX → 建 GitHub Release 并挂上它 →
发布到 VS Code Marketplace 与 Open VSX。

```bash
# 先改 apps/vscode/package.json 的 version 与 CHANGELOG.md，提交
git tag v0.2.0 && git push origin v0.2.0
```

版本号对不上会**在打包之前**失败 —— Marketplace 认的是清单里那个版本，
发错了收不回来。

两个商店的令牌配在仓库的 `marketplace` 环境里（Settings → Environments）：

| Secret     | 用途                | 申请处                                                   |
| ---------- | ------------------- | -------------------------------------------------------- |
| `VSCE_PAT` | VS Code Marketplace | Azure DevOps 个人访问令牌，scope 选 Marketplace → Manage |
| `OVSX_PAT` | Open VSX            | <https://open-vsx.org> 登录后在 Settings 里生成          |

**没配令牌也能用**：对应的发布步骤会自动跳过，GitHub Release 照常创建，
用户可以下载 VSIX 手动安装。给这个环境加一条人工审批，就能杜绝「打错 tag 直接
发上商店」。

每次 PR 的 Artifacts 里也有一份 VSIX（保留 14 天），正式发布前想让人试用就用它。

## 部署

推送到 `main` 后由 GitHub Actions 构建并发布到 GitHub Pages。项目页部署在 `/<repo>/` 子路径下，构建时通过 `BASE_PATH` 环境变量注入。

## 关于 `design/`

`design/` 里是本项目的 Claude Design 原型存档（`.dc.html` + 运行时 `support.js`），仅作设计参考，不参与构建，也被 ESLint / Prettier 忽略。

原型验证了交互设计，但它在浏览器里从 CDN 拉 React UMD + Babel standalone 现场编译，没有构建、类型、测试，断网打不开。当前版本是在保留其视觉与交互的前提下重写的工程化实现，同时修复了原型中 21 项已定位缺陷（端口身份、编解码、流生命周期、渲染性能、背压、重连策略等）。

## Roadmap

尚未实现，按需求优先级排列：

- 多字符编码（GBK / Big5 / Shift_JIS 等）—— 文本收发目前固定 UTF-8
- 真实端口名（COM3）与同型号设备区分 —— 需要本地辅助程序（Node `serialport` / Python `pyserial`）或打包成 Tauri 桌面应用；浏览器 API 做不到
- 日志虚拟滚动（当前渲染上限 600 行，环形缓冲容量 5000 条）
- DTR / RTS 信号控制与 Break
- 日志多格式导出（CSV、二进制）
- 数据波形绘图
